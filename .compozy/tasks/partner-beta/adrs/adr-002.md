# ADR-002: Ledger Data Model

## Status

Accepted

## Date

2026-07-24

## Context

The Partner Beta requires tracking manual payments from businesses and managing their active status. The PRD requests a basic ledger for the Admin Dashboard to log payment date, value, and duration in months, and a manual toggle for the active state.

## Decision

We will create a new `partner_ledger` table to record the payment history (amount, months, date). We will also add an `expirationDate` column to the `businesses` table. When an admin logs a payment, it adds a row to `partner_ledger` and can optionally update the `expirationDate` and `isActive` fields on the `businesses` table. This keeps the ledger as an append-only log of payments, while the `businesses` table remains the single source of truth for the current active state and expiration.

## Alternatives Considered

### Alternative 1: Calculate state from ledger on-the-fly
- **Description**: Do not add `expirationDate` or `isActive` to `businesses`; instead, calculate them dynamically by summing the months in the ledger.
- **Pros**: Single source of truth.
- **Cons**: Requires joining the ledger table for every business query to check if they are active, which adds unnecessary overhead for a simple MVP.
- **Why rejected**: Slower queries and more complex logic for the frontend.

## Consequences

### Positive
- Fast, simple queries for the active state (`isActive` is already a boolean on the business).
- Audit trail preserved in the new ledger table.

### Negative
- Requires maintaining sync between the ledger entries and the business profile's `expirationDate` via the application layer.

### Risks
- Application bugs could cause the `expirationDate` to drift from the actual ledger entries.
- **Mitigation**: The admin has manual override capability on the `isActive` switch and `expirationDate` to correct any issues.
